  1. Add detailed few-shot examples showing the correct tool sequence for each booking workflow.
  2. Rewrite all 12 tool descriptions with explicit “use this ONLY when” boundaries and input/output specifications.
  3. Split the agent into role-scoped subagents (search agent, booking agent, post-booking agent) with 4–5 tools each.
  4. Implement a rule engine that validates tool call sequences and rejects invalid transitions.

A code migration agent uses fork_session to explore two refactoring strategies in parallel. After both branches complete, the coordinator selects the approach with fewer breaking test failures. However, when the coordinator attempts to apply the winning strategy, it regenerates the code from scratch instead of using the fork’s output — introducing new bugs that were not present in the fork’s version.

What is the most likely root cause?
  1. fork_session branches are read-only snapshots — their file modifications cannot be directly applied to the main session’s working directory.
  2. The coordinator’s context was summarized between the fork completion and the application phase, losing the specific implementation details.
  3. The coordinator’s prompt does not include explicit instructions to reuse fork output rather than regenerating.
  4. The fork_session output was not serialized into a format the coordinator could consume as structured input.

CORRECT ANSWER

QUESTION 2 — AGENTIC ARCHITECTURE & ORCHESTRATION
Coordinator uses fork_session to explore strategies; winning fork’s code gets regenerated from scratch instead of reused. Most likely root cause?
Correct Answer: C
The coordinator’s prompt does not include explicit instructions to reuse fork output rather than regenerating.
fork_session branches the conversation history, not the filesystem. Files written inside a fork are real and remain in the shared working directory — any session in the same directory can see them. So the winning approach’s edits are already on disk; the coordinator regenerates only because nothing in its prompt tells it to build on the files that are already there. The fix is to instruct the coordinator to reuse the existing working-directory changes (or capture which fork won and point it at those files).
Why the others are wrong: A — false: forks are not read-only snapshots. Forking branches the conversation, not the filesystem, so a fork’s file edits do persist in the shared working directory. B — no summarization event is described, and the winning code is on disk regardless of context state. D — serialization is irrelevant; the files already exist in the working directory — they do not need to be serialized as structured input.

CORRECT ANSWER

A research agent is tasked with analyzing a 200-page technical specification. It reads the document in chunks, accumulating findings from previous chunks in its context as it processes each subsequent chunk. Reviewers notice that findings from pages 80–140 are consistently thinner and less detailed than findings from the beginning (pages 1–40) and end (pages 160–200) of the document. No errors occur during processing.

What is the most likely explanation and fix?
  1. The document’s middle section contains less substantive content — the thin findings accurately reflect less important material.
  2. The agent’s context window fills up by the middle sections, causing implicit truncation. Fix: use a model with a larger context window.
  3. The “lost in the middle” effect causes the model to process the beginning and end of its context more reliably. Fix: place a running summary at the START of each chunk’s prompt containing accumulated key findings.
  4. The chunking strategy creates uneven chunk sizes with the middle chunks being smaller. Fix: ensure all chunks have equal token counts.

CORRECT ANSWER

QUESTION 9 — CONTEXT MANAGEMENT & RELIABILITY
Research agent produces thinner findings for pages 80–140 vs beginning/end of a 200-page document. No errors. Most likely explanation?
Correct Answer: C
The “lost in the middle” effect causes the model to process the beginning and end of its context more reliably. Fix: place a running summary at the START of each chunk’s prompt containing accumulated key findings.
The “lost in the middle” pattern is well-documented — models attend more reliably to the beginning and end of their context window.
